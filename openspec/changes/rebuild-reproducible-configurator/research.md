## Questions

1. What are the documented, supported mechanisms for reproducibly installing Pi packages from npm and local source checkouts, including update behavior and project/global scope?
2. How should a machine configurator safely manage development-branch checkouts of gentle-ai and gentle-pi while preserving dirty worktrees and recording the exact resolved commit?
3. Which Pi/Gentle AI configuration files are user-owned versus package-managed, and what documented mechanisms should be used instead of copying generated assets?
4. What secret-reference mechanisms does pi-web-access support for API credentials, and which authentication steps must remain interactive/local?
5. What stable commands or observable states can enable and verify global RDD mode without fabricating review authority?
6. What evidence can safely determine when the temporary Pi `sdd-research` override should retire in favor of official packaged support?
7. What XDG-compliant state/receipt structure and Git-tag checkpoint semantics best fit a private single-maintainer machine configurator?

## Validated claims

Claims map to source IDs; each claim was checked against the bounded excerpts above.

### Q1 — Pi package installation, update behavior, scope

- C1: Pi accepts npm (`npm:@scope/pkg@1.2.3` / `npm:pkg`), git (`git:host/user/repo@ref` or protocol URLs), and local path sources; local paths are added to settings **without copying** and relative paths resolve against the settings file they appear in. [S2]
- C2: Versioned npm specs are pinned and skipped by package updates (`pi update --extensions`, `pi update --all`); user-scoped installs go under `~/.pi/agent/npm/`, project-scoped under `.pi/npm/`; `npmCommand` in settings.json pins the npm wrapper for all npm operations. [S2, S1]
- C3: `pi install`/`remove` default to user settings `~/.pi/agent/settings.json`; `-l` writes project settings `.pi/settings.json`; Pi auto-installs missing project packages at startup once the project is trusted; project settings override global settings (nested merge). [S2, S1]
- C4: Git-package refs are pinned tags or commits; updates never move them to newer refs but reconcile the existing clone to the configured ref; **when reconciliation changes the checkout, pi resets and cleans the clone, then runs `npm install`**. [S2]
- C5: Package identity for dedup: npm by name, git by repository URL without ref, local by resolved absolute path; project entry wins over global unless the project entry has `autoload: false`. [S2]
- C6: Pi packages run with full system access; the docs instruct reviewing source before installing third-party packages. [S2]
- C7: A local path package (e.g. `../../Projects/gentle-pi`) references the source checkout without copying, so reproduction can reuse existing dev checkouts directly as package sources. [S2]

### Q2 — Safe management of dev-branch checkouts

- C8: Plain `git checkout` refuses to switch branches when local modifications differ between branches (preserving them); `--force` throws away local changes and untracked files; checking out a bare commit detaches HEAD for inspection/discardable experiments. [S14]
- C9: `git fetch` updates refs subject to fast-forward rules; updates to `refs/heads/*` and `refs/tags/*` are rejected without `+`/`--force` when non-fast-forward (tags since Git 2.20); `--no-tags`, `--prune`, `--prune-tags` control tag handling. [S16]
- C10: Pi's own git-package reconciliation is destructive to dirty worktrees (reset + clean before `npm install`), so dev checkouts with local work must not be managed through Pi's git-package reconcile path; preserving dirty worktrees is additionally required by the local exploration/OpenSpec `apply.preserve_dirty_worktree: true`. [S2 + exploration; preservation requirement is local policy, not upstream doc]
- C11: The exact resolved commit of a checkout is recordable via the pinned-ref + `rev-parse` idiom the Pi docs assume for git refs; annotated tags are release-oriented, lightweight tags are private/temporary labels that `git describe` ignores by default. [S2, S15]

### Q3 — User-owned vs package-managed configuration

- C12: Pi global settings live in `~/.pi/agent/settings.json` (packages array included); project settings in `.pi/settings.json`; both are edited directly or via `/settings` — these are user-owned files. [S1]
- C13: Pi context files: `AGENTS.md`/`CLAUDE.md` from `~/.pi/agent/AGENTS.md` plus cwd/parents; `SYSTEM.md` replaces the default prompt; `APPEND_SYSTEM.md` appends without replacing (project or global). [S17]
- C14: gentle-pi's package-managed assets (SDD agents, chains, skills, and the package-local Gentle AI v2.4.0 binary) are provisioned by the package postinstall (`scripts/install-gentle-ai.mjs`), integrity-validated, and reject PATH/global/sibling/symlink fallbacks; `GENTLE_PI_SKIP_GENTLE_AI_INSTALL=1` is a development/offline escape hatch that makes native review fail closed with `package-local-binary-missing`. [S5, S6, S7]
- C15: gentle-ai managed assets are version-bound to the binary and refreshed via `gentle-ai sync` after upgrades. [S10]
- C16: Official gentle-ai guidance explicitly says do NOT manually edit generated config files or patch skill files — regeneration via the installer/sync is the documented mechanism for package-managed content. [S12]

### Q4 — pi-web-access secret references and interactive/local auth

- C17: Provider API credentials in `~/.pi/web-search.json` accept three forms: literal value, environment-variable reference (`$NAME` / `${NAME}`), or trusted local command source (`!command`), resolved at provider request time; interpolation applies to provider credentials only, never other config fields. [S3, S4]
- C18: Environment-variable equivalents (e.g. `OPENAI_API_KEY`, `EXA_API_KEY`, `GEMINI_API_KEY`, `PERPLEXITY_API_KEY`, `CLOUDFLARE_API_KEY`) retain precedence over literal config values; an explicit source overrides legacy env vars and fails locally rather than falling back to a stale credential. [S4]
- C19: Zero-config authentication is interactive: Exa MCP (no key), Codex auth reuse via `/login`, Kimi Code Plan via `/login kimi-coding`; these are per-machine runtime steps, not catalogable configuration. [S3, S4]
- C20: `authFetch` named browser-cookie profiles and a `browserCookies` preset provide opt-in cookie-based access; the web-search cache is private (0700/0600) and bounded (1-hour lifetime, 128 entries / 128 MiB). [S4]
- C21: Command credential sources are trusted local configuration (not a same-user isolation boundary), run per request with a 5-second timeout and 16 KiB output cap; `OP_SESSION_*` is forwarded for 1Password reuse; absolute executable paths and config-file protection are advised. [S4]

### Q5 — RDD global mode: commands and observable states

- C22: `gentle-ai review mode enable --scope global` is the only command that turns RDD on; `gentle-ai review mode status --cwd <repo>` reports the global source, clone-local source, deciding source, and effective mode **without mutation**; disable commands exist for global and clone scopes. [S11]
- C23: With no source expressing an opinion, RDD is off and status reports `default` as deciding source; any disabled source wins; a clone can opt out but only the global scope can require review. [S11]
- C24: Native delivery gates report `disabled/unmanaged` when no exact receipt applies and never fabricate approval; while disabled, work continues through ordinary routing without starting, retrying, or re-enabling review. [S11]
- C25: RDD is opt-in by default since gentle-ai v2.4.0 (breaking change) and gentle-pi's RDD line starts at v0.15.0 (stable v0.14.0 without RDD); ordinary repository policy decides delivery regardless of mode. [S10, S7, S12]

### Q6 — Retirement of the temporary sdd-research override

- C26: Official source-backed SDD Research is implemented on gentle-ai main (issue #3588 closed/completed via PR #3590) and ships as of v2.5.0-rc.1 with `/sdd-research <questions>`, `gentle-ai.sdd-research-capability/v1` admission, and a `gentle-ai.sdd-research/v1` artifact persisted under `openspec/changes/{change-name}/research…`. [S9, S18, S8]
- C27: As of access date, the latest **stable** gentle-ai is v2.4.0 (no sdd-research phase); v2.5.0-rc.1 is a prerelease candidate. Retirement evidence must therefore be the official phase present in a **consumed stable release** (or an explicitly consumed release the environment exposes `/sdd-research` on), verified against the installed binary/version and the managed-assets manifest — not merely upstream main. [S9, S10]
- C28: The official lane's contract (Closed Capability Admission, Auditable Evidence Integrity, Hybrid Completion and Recovery with fail-closed divergence) matches the temporary override's behavior, supporting retirement to the managed asset once the release predicate holds. [S8]

### Q7 — XDG state/receipt structure and Git-tag checkpoints

- C29: `$XDG_STATE_HOME` (default `~/.local/state`) is the spec-defined location for user-specific state persisting across restarts (logs, history, current application state); data/cache/runtime have separate homes (`~/.local/share`, `~/.cache`, `$XDG_RUNTIME_DIR` with 0700, login-bound lifetime, local-only, non-persistent); all paths must be absolute. [S13]
- C30: Annotated tags carry date/tagger/message (and optional signature) and are meant for release; lightweight tags are private/temporary labels that `git describe` ignores by default. [S15]
- C31: Tags are fetched by default; updating `refs/tags/*` requires fast-forward or explicit `+`/`--force` since Git 2.20 — checkpoint tags should be annotated (descriptive, discoverable) and moved only with force semantics. [S16, S15]
- C32: Pi's own runtime state intentionally does NOT follow XDG: user packages land under `~/.pi/agent/npm/` and git packages under `~/.pi/agent/git/` (fixed home-relative dirs). A configurator's own receipts may follow XDG per C29, but must not expect Pi's runtime state to be XDG-compliant. [S2, S13]

## Contradictions, uncertainty, freshness

- **`~/.pi/npm/` vs `~/.pi/agent/npm/`**: Pi docs (S1/S2) state user npm installs go under `~/.pi/agent/npm/`; the corrected local exploration observed `~/.pi/npm/package.json` (with `pi-mcp-adapter ^2.6.0`). Likely a version difference between installed Pi and docs at `latest`; the catalog should record the directory it must reproduce and verify against the installed Pi, not assume one path.
- **RDD default**: exploration records the machine as globally enabled (user's explicit desired state); upstream docs (S11/S10) confirm off-by-default since v2.4.0 and that explicit `enable --scope global` is the only way on. No contradiction — reproduction must explicitly enable.
- **sdd-research availability**: exploration said official support is "near"; S9/S18 now confirm it ships in v2.5.0-rc.1 (prerelease) with stable still at v2.4.0. The retirement condition is therefore a concrete release predicate, not a guess; prerelease rc.1 is not sufficient evidence that the consumed stable environment ships it.
- **APPEND_SYSTEM.md ownership**: Pi docs (S17) document it as a user mechanism ("append to the default prompt without replacing it"); gentle-ai/gentle-pi additionally write runtime-generated contract text into it (per exploration §3.3). The two ownership views conflict in that a file both tools write cannot be purely user-owned; the split (user overlay + regenerated sections) remains a product decision.
- **Web-search credential shape**: docs show literal keys in `~/.pi/web-search.json` (S3/S4) but also env/command references; the machine's file contains live values (per exploration, not read). Catalog must use reference forms only.
- **Freshness**: access date 2026-08-29; Pi docs at `latest`; gentle-pi 2.2.0; gentle-ai v2.4.0 stable / v2.5.0-rc.1 prerelease; pi-web-access 0.27.0 requires Pi v0.37.3+. Version-sensitive claims (C2, C4, C9, C17, C22, C26, C27, C31) must be re-verified when the catalog pins newer releases.
