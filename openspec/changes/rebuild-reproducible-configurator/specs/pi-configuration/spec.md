# Pi Configuration Specification

## Purpose

Reproduces the user-owned Pi/Gentle AI configuration: the exact-pinned Pi package
set including the local `gentle-pi` path package, the user-owned versus
package-managed file split (including `AGENTS.md` versus `APPEND_SYSTEM.md`), and
the managed-asset verification-only rule. Credential values and biometric data are
never cataloged; auth remains interactive.

## Requirements

### Requirement: Exact-pinned Pi package set

The catalog MUST declare the Pi package set as explicit npm specs with exact
versions, with the local `gentle-pi` checkout referenced as a relative path package
(`../../Projects/gentle-pi`) resolved against the settings file location, and with
`npmCommand` pinned if used. The configurator MUST drive installs from the catalog
rather than relying on `pi update --all`; exact-pinned specs are skipped by Pi's
update commands, which is what makes the set reproducible.

#### Scenario: Catalog pins drive the install

- GIVEN a fresh machine with the catalog's exact-pinned Pi package set
- WHEN the Pi install step runs
- THEN each catalog spec is installed at its exact version under user scope

#### Scenario: Local path package resolves against the settings file

- GIVEN the catalog entry `../../Projects/gentle-pi`
- WHEN the package is resolved
- THEN it resolves to the local checkout relative to the settings file location and is referenced without copying

### Requirement: Desired pins versus resolved Pi versions

Catalog exact pins define the desired Pi package state. Resolved versions observed
in the installed Pi package state MUST be recorded as `resolvedInstalledVersions`
in receipts for audit only and MUST NOT redefine the desired pins. `check` MUST
report drift between desired exact pins and resolved versions. The documented
install directory divergence (`~/.pi/agent/npm` versus `~/.pi/npm`) MUST be handled
by recording the intended directory in the catalog and probing both at check time
against the installed Pi version, rather than assuming one path.

#### Scenario: Pi version drift is reported

- GIVEN a catalog exact pin and a differently resolved installed version
- WHEN `check` runs
- THEN the drift is reported and the desired pin is unchanged

#### Scenario: Install-directory divergence is probed, not assumed

- GIVEN installed Pi whose package directory differs from the documented default
- WHEN `check` probes package presence
- THEN it probes both documented locations and reports which one holds the packages

### Requirement: User-owned cataloged files

The catalog MUST include, as user-owned desired state: the minimal
`~/.pi/agent/settings.json` shape (model, provider, thinking level, changelog
marker, packages, theme — without `session_resources`, `default_mode`,
`enable_continue`, `debug`, or `model_profiles`), `~/.pi/agent/subagents.json`
(`session_resources: lean`, `default_mode: task`, `enable_continue: false`,
`debug: false`, plus the 23 model profiles with effort levels),
`~/.pi/gentle-ai/models.json` (the 23 routes with thinking levels),
`~/.pi/gentle-ai/persona.json`, `~/.pi/gentle-ai/background-subagents.json`,
`~/.pi/agent/AGENTS.md`, the secret-free `~/.pi/web-search.json` template, and the
temporary `~/.pi/agent/subagents/sdd-research.md` override. These files MUST be
rendered from the catalog, not copied from a captured machine.

#### Scenario: User-owned files render from the catalog

- GIVEN a fresh machine and the merged catalog
- WHEN the Pi configuration steps run
- THEN `settings.json` matches the minimal shape, `subagents.json` contains the lean/task settings and 23 profiles, `models.json` contains the 23 routes, and `persona.json`/`background-subagents.json` match their catalog shapes

### Requirement: AGENTS.md user-owned, APPEND_SYSTEM.md package-managed

User environment guidance MUST live in `~/.pi/agent/AGENTS.md` as the user-owned
overlay; `APPEND_SYSTEM.md` MUST remain fully package-managed by Gentle Pi with
append (not replace) semantics. The configurator MUST NOT copy, merge into, or
overwrite `APPEND_SYSTEM.md` with user content, and MUST NOT treat the combined
file as an opaque blob. Regeneration of package-managed content happens through
the harness install path plus `gentle-ai sync`, after which the split is verified.

#### Scenario: User guidance lands in AGENTS.md only

- GIVEN the catalog's user environment guidance for the CachyOS+niri+Noctalia and pkexec context
- WHEN the Pi configuration steps run
- THEN the guidance is written to `~/.pi/agent/AGENTS.md` and `APPEND_SYSTEM.md` is not modified by the configurator

#### Scenario: Package-managed content is regenerated, not copied

- GIVEN a completed harness install followed by `gentle-ai sync`
- WHEN `APPEND_SYSTEM.md` is inspected
- THEN its runtime contract text is regenerated by the package and the user's environment guidance remains in `AGENTS.md`

### Requirement: Package-managed assets verified, never vendored

Package-managed assets (managed assets manifest, support docs, chains, agent
prompts, and the package-local Gentle AI binary) MUST be treated as install
outputs of the selected local-main gentle-pi checkout, refreshed by the postinstall
or local-main path plus `gentle-ai sync`, and MUST be verified against the
`managed-assets.json` SHA-256 manifest after installation. The configurator MUST
NOT copy these assets verbatim from a captured machine as its primary installation
path.

#### Scenario: Managed assets verify against the manifest after install

- GIVEN a completed harness install
- WHEN verification runs
- THEN the installed managed assets match the `managed-assets.json` SHA-256 manifest

#### Scenario: Verbatim vendoring is rejected

- GIVEN a proposed install path that copies managed assets from a captured machine
- WHEN the plan is validated against the catalog ownership rules
- THEN the path is rejected because managed assets must be install outputs

### Requirement: Interactive auth is never cataloged

Authentication (Codex `/login`, Kimi `/login kimi-coding`, browser-cookie opt-in,
and future provider OAuth) MUST remain interactive per-machine runtime steps after
`apply`. The configurator MUST NOT read `auth.json` or any credential store, and
MUST detect the authenticated-but-not-cataloged state via status probes rather than
file reads. Interactive login steps MUST be documented as post-apply manual steps.

#### Scenario: No credential file is read during a run

- GIVEN an `apply` or `check` run
- WHEN file access is audited
- THEN `auth.json`, keyring content, and credential caches are never read

#### Scenario: Authenticated state is probed, not read

- GIVEN a machine where provider authentication has been completed interactively
- WHEN the configurator assesses authentication state
- THEN it uses status probes and never parses `auth.json`
